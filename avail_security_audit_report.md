# Avail Core Protocol: Security Audit Report - `avail-core/core/src`

## 1. Introduction

This document presents the findings of a security audit focused on the `avail-core/core/src` codebase of the Avail protocol. The primary goal of this audit was to identify critical and high-impact vulnerabilities that could compromise the security, integrity, or availability of the Avail network, with a particular emphasis on issues that could lead to exploits as outlined in typical Web3 security concerns.

The methodology employed was primarily static analysis of the Rust codebase within the `avail-core/core/src` directory. This involved a manual review of the code, focusing on logic flaws, potential cryptographic misuse, data validation practices, error handling, and structural concerns relevant to the identified potential vulnerabilities. The analysis leveraged understanding gained from previous documentation of the Avail core components, data structures, and user flows.

The scope of this audit is strictly limited to the code within the `avail-core/core/src` directory and its subdirectories. It does not extend to a full audit of the entire Substrate framework upon which Avail is built, nor does it cover client-side applications, smart contract logic (if any, beyond core runtime primitives), or live network penetration testing.

## 2. Executive Summary

The audit of `avail-core/core/src` identified several areas of concern, including one critical bug related to cryptographic hashing and multiple areas where the security heavily relies on correct and robust integration by the consuming Avail runtime.

**Most Critical Finding:**
*   A critical bug was found in the `ShaTwo256` implementation (`core/src/sha2.rs`), where it incorrectly uses `keccak_256` instead of a SHA2-256 hash function. This could lead to unexpected cryptographic behavior, signature validation failures if SHA2-256 is assumed, and potential interoperability issues.

**Key Observations:**
*   The `avail-core` module provides foundational building blocks for data availability. Its security is intrinsically linked to how it is integrated and configured within the broader Avail node runtime.
*   Several components, such as `AppExtrinsic` handling, `HeaderExtension` construction, and `AppId` management, present significant integration points where runtime misconfiguration or inadequate validation could introduce vulnerabilities.
*   The design allows for nested extrinsic processing (`AppExtrinsic.data`), which places a substantial responsibility on the runtime to manage resources, depth, and potential exploits within these nested calls.

While `avail-core/core/src` itself appears to be a relatively focused library, its interaction points with the runtime are critical. Therefore, a comprehensive security assessment of the Avail protocol must include a thorough audit of the consuming runtime environment.

## 3. Detailed Findings

### F1: Critical Bug - Incorrect Hash Function in `ShaTwo256`

*   **File:** `core/src/sha2.rs`
*   **Description:** The `ShaTwo256::hash` function is implemented using `keccak_256` instead of a standard SHA2-256 hashing algorithm.
    ```rust
    // From core/src/sha2.rs
    impl sp_core::Hasher for ShaTwo256 {
        type Out = H256;
        fn hash(s: &[u8]) -> Self::Out {
            keccak_256(s).into() // Should be a SHA2-256 implementation
        }
    }
    ```
*   **Impact:**
    *   **Cryptographic Mismatch:** If any part of the system or external integrations expect a standard SHA2-256 hash, using Keccak256 will lead to mismatches, validation failures, and potential security vulnerabilities if cryptographic properties differ significantly in a specific context.
    *   **Incompatibility:** Systems expecting SHA2-256 hashes will not be able to correctly verify or interoperate with hashes generated by this function.
    *   **Unexpected Properties:** While Keccak-256 is secure, using it where SHA2-256 is named and expected can violate security assumptions made elsewhere in the system or by users.
*   **Likelihood:** High (the incorrect implementation is present).
*   **Severity:** Context-dependent (Medium to High). If this hash is used in critical security paths where SHA2-256 properties are specifically relied upon (e.g., certain signature schemes or cross-chain verifications), the severity is High. If its usage is limited and the properties of Keccak256 are acceptable by chance, the impact might be lower but still represents a significant correctness issue.
*   **Recommendation:** Replace the `keccak_256` call within `ShaTwo256::hash` with a proper SHA2-256 hashing function implementation from a reputable cryptographic library (e.g., `sha2` crate).

### F2: Potential Integration Vulnerability - `AppId` Handling and Defaulting

*   **Files:** `core/src/app_extrinsic.rs`, `core/src/asdr.rs`, `core/src/traits/get_app_id.rs`
*   **Description:**
    *   `AppExtrinsic` includes an `app_id: AppId`.
    *   The `GetAppId` trait has a default implementation: `fn app_id(&self) -> AppId { AppId::default() }` which typically results in `AppId(0)`.
    *   `AppExtrinsic::from(unchecked_extrinsic)` attempts to get `app_id` from the `SignedExtension`, but falls back to `AppId::default()` if the signature is missing or the extension doesn't provide it.
*   **Concern:** If `AppId(0)` has special privileges, bypasses certain checks, or is treated differently by the runtime logic (e.g., for fee calculations, data routing, or permissions), then extrinsics that incorrectly default to or are forced to use `AppId(0)` could lead to unintended consequences.
*   **Potential Impact:**
    *   **Privilege Escalation:** If `AppId(0)` has elevated permissions.
    *   **Fee Evasion:** If `AppId(0)` transactions have different fee structures.
    *   **Logic Bypass/Exploitation:** If runtime logic branches significantly based on `AppId(0)`.
    *   **Data Inconsistency:** If data attribution becomes ambiguous or incorrect.
*   **Recommendation:**
    *   The Avail runtime must meticulously define and restrict the permissions and behavior associated with `AppId(0)`.
    *   Ensure all `SignedExtension`s designed to carry `AppId` information reliably provide it.
    *   Consider removing the default implementation of `GetAppId::app_id()` from `core/src/traits/get_app_id.rs` to force explicit `AppId` handling in all implementations, making it a compile-time error if an `AppId` source is not clearly defined for types that need it. This would make the runtime's responsibility clearer.

### F3: Architectural Risk - Nested Extrinsic Processing (`AppExtrinsic.data`)

*   **Files:** `core/src/app_extrinsic.rs`, `core/src/asdr.rs` (Application Specific Data Routing)
*   **Description:** The `AppExtrinsic::data` field is a `Vec<u8>`. The `asdr.rs` (Application Specific Data Routing) logic implies this data can be interpreted and dispatched as another extrinsic by the runtime. This creates a scenario of nested extrinsic processing.
*   **Concern:** The security of processing these nested extrinsics relies heavily on the consuming runtime's implementation. Key concerns include:
    *   **Resource Limiting:** Nested calls can lead to recursion or computational bombs if not strictly limited in depth and weight/gas.
    *   **WASM Exploits:** If the inner extrinsic is a WASM call, vulnerabilities in that WASM or its execution environment could be triggered.
    *   **Atomicity and State Reversion:** Ensuring that if an inner extrinsic fails, the state changes are correctly rolled back or handled without corrupting the outer transaction's state or the overall block state.
    *   **Fee Logic:** How fees are calculated and charged for nested calls needs careful consideration to prevent economic exploits.
*   **Potential Impact:**
    *   **DoS:** Through resource exhaustion (computation, memory, recursion depth).
    *   **WASM Exploits:** Leading to unauthorized state changes or runtime traps.
    *   **State Inconsistencies:** If error handling or atomicity is not properly managed.
    *   **Economic Vulnerabilities:** Related to fee calculation for nested operations.
*   **Recommendation:**
    *   The Avail runtime must implement robust controls for nested extrinsic dispatch originating from `AppExtrinsic.data`.
    *   Strictly enforce limits on recursion depth (e.g., using mechanisms like `InvalidTransactionCustomId::MaxRecursionExceeded`, ensuring its checks are effective).
    *   Implement accurate weight/gas accounting for inner calls and ensure it contributes to the outer extrinsic's limits.
    *   Thoroughly test error handling and state rollback mechanisms for nested calls.

### F4: Critical Integration Point - `HeaderExtension` Integrity and Construction

*   **Files:** `core/src/header/mod.rs`, `core/src/header/extension/mod.rs`, `core/src/header/extension/v3.rs`, `core/src/kate_commitment.rs`, `core/src/data_lookup/mod.rs`
*   **Concern:** The integrity of the `HeaderExtension` is paramount for the DA scheme. Several critical relationships must be maintained by the runtime during block construction:
    *   **`KateCommitment.data_root` Consistency:** The `data_root` field within `KateCommitment` (stored in the header) *must* accurately reflect the Merkle root of the actual transaction data that was erasure-coded (i.e., it should match `TxDataRoots.blob_root`). Any discrepancy breaks the link between DA proofs and inclusion proofs.
    *   **`DataLookup` Correctness:** The `app_lookup` structure must be correctly built based on the `AppId`s and data indices from the block's extrinsics. Errors here could prevent correct data retrieval or attribution.
    *   **Kate Matrix Dimensions (`rows`/`cols`):** These dimensions, stored in `KateCommitment`, dictate the size of the DA problem. The runtime must impose sensible, tested limits on these values to prevent DoS (e.g., excessively large matrices requiring huge commitments or causing OOM errors during processing/verification) or inefficient DA.
    *   **Misuse of Helper Functions:** Functions like `HeaderExtension::get_empty_header()` and `HeaderExtension::get_faulty_header()` are provided. If these are used inappropriately in production block construction with inconsistent `data_root` values, it could lead to invalid states or bypass DA checks.
*   **Potential Impact:**
    *   **Data Availability Failure:** Light clients might be unable to verify data availability or might be tricked into accepting unavailable data if commitments are incorrect.
    *   **Invalid Inclusion Proofs:** If `KateCommitment.data_root` doesn't match the actual data root, `DataProof`s become meaningless.
    *   **Denial of Service:** By crafting extrinsics that lead to excessively large DA parameters (if not limited by the runtime) or malformed `HeaderExtension` data that causes processing errors.
    *   **Chain Instability:** If nodes disagree on the validity of `HeaderExtension` data.
*   **Recommendation:**
    *   The Avail runtime must have strict validation and consistency checks ensuring `KateCommitment.data_root` equals the `blob_root` of the data it commits to.
    *   The runtime must correctly and robustly build the `app_lookup` structure, handling potential errors or edge cases.
    *   Implement and enforce practical, well-tested upper bounds on `KateCommitment.rows`, `KateCommitment.cols`, and the total number of entries in `app_lookup` within the runtime.
    *   Ensure that `HeaderExtension::get_empty_header()` and `HeaderExtension::get_faulty_header()` are used only in appropriate contexts (e.g., genesis block construction, specific error handling scenarios) and not as a means to bypass DA for regular blocks.

### F5: General Robustness - Error Handling and Resource Limits

*   **Description:** The `avail-core/core/src` codebase generally uses `Result` and `Option` for error handling, which is good practice. Constants like `BLOCK_CHUNK_SIZE` (in `da_block.rs`, though not explicitly shown in provided snippets, it's a common pattern) and `DA_DISPATCH_RATIO` (likely related to how much block space can be DA data) are defined.
*   **Concern:**
    *   **Error Propagation:** The consuming runtime must diligently handle all error conditions returned by `avail-core` APIs. Unhandled errors or panics in the runtime due to unexpected results from core functions can lead to node crashes.
    *   **Resource Limits:** While `avail-core` might define some constants, the ultimate enforcement of resource limits (e.g., maximum size of `AppExtrinsic.data` that feeds into the Kate matrix, maximum number of extrinsics, computational limits for DA processing) rests with the runtime. Without these, malicious inputs could lead to DoS.
*   **Potential Impact:**
    *   **Node Instability/Crashes:** If runtime panics due to unhandled errors from core logic.
    *   **Denial of Service:** Resource exhaustion attacks if the runtime doesn't enforce limits on data sizes, matrix dimensions, or computational complexity related to DA processing.
*   **Recommendation:**
    *   The Avail runtime must implement comprehensive error handling for all calls into `avail-core` functions, ensuring graceful degradation or appropriate transaction rejection.
    *   The runtime should enforce strict, configurable resource limits on parameters that affect the DA mechanism (e.g., max `AppExtrinsic.data` size, max `rows` and `cols` for Kate commitments, max entries in `app_lookup`). These limits should be determined based on performance testing and security considerations.
    *   Constants defined in `avail-core` (like `BLOCK_CHUNK_SIZE` if used for data segmentation, or `DA_DISPATCH_RATIO`) should be respected and integrated into the runtime's resource management logic.

### F6: Benchmark-Only Randomness (`BenchRandomness`)

*   **File:** `core/src/bench_randomness.rs`
*   **Description:** This module provides a deterministic source of randomness, explicitly intended for benchmarking purposes.
*   **Concern:** If this predictable randomness source were ever used in production runtime logic for any security-sensitive operation (e.g., choosing block producers, nonces, sampling strategies if they were meant to be unpredictable), it would constitute a critical cryptographic flaw.
*   **Potential Impact:**
    *   **Predictable Outcomes:** Leading to exploitation of consensus, gameable systems, or compromised cryptographic operations.
    *   **Loss of Security Properties:** If used where cryptographically secure randomness is required.
*   **Recommendation:**
    *   Ensure through build configurations, feature flags (`#[cfg(feature = "runtime-benchmarks")]`), and strict code review that `BenchRandomness` is unequivocally confined to benchmarking builds and never compiled into or used by production runtime code.
    *   Consider adding prominent comments and even `#[deprecated]` attributes (if applicable for non-benchmark builds) to further discourage misuse.

## 4. Limitations of the Audit

*   **Scope:** This audit was strictly limited to the `avail-core/core/src` directory. It did not cover the full Avail node runtime (including specific pallet implementations for staking, governance, etc.), client-side applications, or other ecosystem components.
*   **Integration Dependency:** Many identified concerns (F2, F3, F4, F5) are highly dependent on how `avail-core` is integrated and configured by the consuming runtime. Assessing the true exploitability of these often requires examining the runtime's codebase.
*   **External Libraries:** The security of third-party crates (including the Substrate framework itself beyond direct interactions) was generally assumed, except where their usage patterns by `avail-core` introduced potential issues.
*   **Dynamic Analysis:** This audit was based on static code analysis. Dynamic analysis techniques like fuzzing, penetration testing, and live network analysis were not performed.
*   **Economic & Governance Exploits:** The audit focused on technical vulnerabilities. Complex economic exploits or governance attacks are generally out of scope unless they stem directly from a flaw in the `core/src` logic.

## 5. Recommendations Summary

**For `avail-core/core/src` (Direct Code Changes):**

*   **F1 (Critical):** Correct the `ShaTwo256::hash` function in `core/src/sha2.rs` to use a proper SHA2-256 implementation.
*   **F2 (High Potential):** Consider removing or refactoring the default implementation of `GetAppId::app_id()` to make `AppId` provision more explicit and reduce the risk of accidental misuse of `AppId(0)`.

**For the Consuming Avail Runtime (Critical for Overall Security):**

*   **AppId Management (F2):** Rigorously validate and control `AppId` derivation. Clearly define and strictly limit permissions associated with `AppId(0)`. Ensure `SignedExtension`s reliably provide `AppId`s for all application extrinsics.
*   **Nested Extrinsic Handling (F3):** Implement robust security measures for processing nested extrinsics within `AppExtrinsic.data`. This includes strict limits on recursion depth, weight/gas accounting, and comprehensive error handling with correct state rollback.
*   **HeaderExtension Integrity (F4):**
    *   Ensure absolute consistency between `KateCommitment.data_root` (in the header) and the `blob_root` derived from actual transaction data.
    *   Implement robust logic for building the `app_lookup` table, handling all edge cases and potential errors.
    *   Enforce sensible and tested limits on Kate commitment parameters (matrix `rows`, `cols`), `app_lookup` size, and the total data committed per block to prevent DoS and ensure practical DA verification.
    *   Restrict the use of `HeaderExtension::get_empty_header()` and `get_faulty_header()` to only appropriate, well-understood scenarios (like genesis or specific error states).
*   **Error Handling & Resource Limits (F5):**
    *   Implement comprehensive error handling for all API calls to `avail-core` to prevent runtime panics.
    *   Enforce strict resource limits (e.g., maximum data size for `AppExtrinsic.data`, computational limits for DA processing) based on `avail-core` constants and thorough performance/security testing.
*   **Build Configuration (F6):** Ensure that `BenchRandomness` and any other benchmark-specific code are strictly excluded from production runtime builds.
*   **Comprehensive Runtime Audit:** Conduct a thorough security audit of the entire Avail node runtime, including all pallets (especially those handling funds, staking, or governance), `SignedExtension`s, and the integration points with `avail-core`.

## 6. Conclusion

The `avail-core/core/src` codebase provides the foundational elements for Avail's innovative data availability layer. This audit identified one critical bug within the `core/src` module itself (the `ShaTwo256` implementation) that requires immediate attention.

Beyond this direct finding, several architectural aspects and API designs within `avail-core/core/src` highlight the critical importance of secure and careful implementation by the consuming Avail runtime. The security of the Avail network heavily depends on the runtime's diligence in handling `AppId`s, nested extrinsics, the construction and validation of `HeaderExtension` data, resource limiting, and error handling.

While `avail-core/core/src` provides the building blocks, their secure assembly and operation are responsibilities that extend significantly into the runtime layer. A comprehensive security posture for Avail necessitates a thorough audit of the full Avail node runtime in conjunction with the recommendations provided for the core library.
