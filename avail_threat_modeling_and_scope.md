# Avail Core Protocol: Threat Modeling and Audit Scope

## 1. Introduction

The primary goal of this security audit is to identify and help mitigate critical and high-impact vulnerabilities within the `avail-core/core/src` codebase of the Avail protocol. The focus is on uncovering potential weaknesses that could lead to catastrophic failures, unauthorized manipulation of data availability, network instability, or severe data integrity issues, ensuring the robustness and security of Avail's core data availability layer.

## 2. Key Components & Potential Attack Surfaces

The `avail-core/core/src` module is central to Avail's functionality, providing the specialized data availability logic and its integration with the underlying Substrate framework.

## 3. Prioritized Vulnerability Classes (Representative)

Based on common criticalities in blockchain systems and the nature of Avail, the audit will prioritize:

**Critical Impact:**
*   **C1: Unauthorized Fund Loss/Theft/Freezing:** Any vulnerability that could lead to direct loss, theft, or permanent freezing of assets managed by the core protocol (if applicable, e.g., staking or fee mechanisms).
*   **C2: Total Network Unavailability / Permanent Halt:** Vulnerabilities that could cause the entire network to cease block production or enter an unrecoverable state.
*   **C3: Data Availability Layer Failure:** Issues preventing the verification of data availability, such as inability to reconstruct data despite valid commitments, or successful attacks that make data appear available when it is not.
*   **C4: Catastrophic Data Inconsistency/Corruption:** Bugs leading to divergent state views among nodes, incorrect state transitions, or corruption of the blockchain state that is difficult or impossible to recover from.
*   **C5: WASM Execution Exploits (Runtime Logic):** Vulnerabilities within the runtime's WASM execution environment or specific pallets that could allow for unauthorized state changes, privilege escalation, or DoS by exploiting the execution of extrinsics.

**High Impact:**
*   **H1: Denial of Service (DoS) against Block Production or Validation:** Vulnerabilities that allow an attacker to significantly disrupt or halt the block production or validation process, impacting network liveness.
*   **H2: Significant Transaction Censorship or Reordering:** Mechanisms that allow malicious actors to unfairly censor or manipulate the order of transactions beyond expected network latency or mempool dynamics.
*   **H3: Incorrect Proof Generation/Validation:** Flaws in the generation or verification logic for Kate commitments or Merkle proofs (`DataProof`) that could lead to the acceptance of invalid data/proofs or rejection of valid ones, undermining data integrity.
*   **H4: Inflation/Deflation Bugs:** If the core logic includes mechanisms for token issuance or burning, vulnerabilities that could lead to unintended creation or destruction of tokens.
*   **H5: Logic Errors in State Transitions:** Flaws in the core state transition function that lead to incorrect but not necessarily catastrophic state changes, potentially exploitable for gain or disruption.

## 4. Initial Code Areas for Audit Prioritization

Based on the components and prioritized vulnerabilities, the initial static code analysis will focus on, but not be limited to, the following files and modules within `avail-core/core/src/`:

*   **Runtime Entry Points & Core Logic (`lib.rs`):**
    *   Examine the overall runtime structure, dispatch mechanisms, and how core pallets are integrated.
    *   Potential for WASM exploits (C5), DoS (H1), and catastrophic data inconsistency (C4) if core runtime logic is flawed.
*   **Extrinsic Handling (`app_extrinsic.rs`, `asdr.rs` - Application Specific Data Routing):**
    *   Focus on how `AppExtrinsic`s are defined, processed, and how data is extracted and routed.
    *   Vulnerabilities here could lead to DoS (H1), data inconsistency (C4), or issues with `app_lookup` integrity.
*   **Kate Commitments (`kate_commitment.rs`):**
    *   Scrutinize the structure and any logic related to Kate commitments (`rows`, `cols`, `commitment`, `data_root`).
    *   Critical for Data Availability Layer Failure (C3) and Incorrect Proof Generation/Validation (H3).
*   **Data Proofs (`data_proof.rs`):**
    *   Analyze the `DataProof` and `TxDataRoots` structures and any associated verification logic.
    *   Vulnerabilities could lead to Incorrect Proof Generation/Validation (H3) and data inconsistency (C4).
*   **Header Structures (`header/mod.rs`, `header/extension/mod.rs`, `header/extension/v3.rs`):**
    *   Examine the definition of block headers and the critical `HeaderExtension` which carries DA commitments.
    *   Key for Data Availability Layer Failure (C3), Catastrophic Data Inconsistency (C4), and DoS (H1) if malformed headers can crash nodes.
*   **Block Definition (`da_block.rs`):**
    *   Review how blocks are structured and validated.
    *   Potential for DoS (H1) and Data Inconsistency (C4).
*   **Trait Definitions (`traits/`):**
    *   Understand the interfaces defined for extended blocks and headers, as these dictate how core DA logic interacts with Substrate primitives.
    *   Flaws here could have wide-ranging impacts.

## 5. Out of Scope (Assumptions)

The following areas are considered out of scope for this initial static analysis of `avail-core/core/src`:

*   **Full Substrate Framework Audit:** While Avail builds upon Substrate, this audit will focus on the custom code within `avail-core/core/src`. Vulnerabilities in the underlying Substrate framework will only be noted if they are directly exploitable or exacerbated by Avail's custom logic. It is assumed that the version of Substrate used has undergone its own security assessments.
*   **Cryptography Primitives Implementation:** The correctness of underlying cryptographic libraries (e.g., for hashing, signatures, Kate commitments themselves if pre-compiled libraries are used) is assumed, unless Avail implements these directly within `core/src`. The focus will be on the *usage* of these primitives.
*   **Live Network Analysis:** This audit phase does not include penetration testing, monitoring of live networks, or analysis of node interactions beyond what can be inferred from the codebase.
*   **Fuzzing and Dynamic Analysis:** While highly recommended for a comprehensive security assessment, fuzzing and other dynamic analysis techniques are outside the scope of this initial static code review.
*   **Client-Side Applications & Wallets:** Any applications, wallets, or UIs that interact with the Avail network are out of scope.
*   **External Dependencies (beyond Substrate):** The security of third-party Rust crates used will be assumed unless glaring issues are identified during the review of their integration. A full audit of all dependencies is not included.
*   **Social Engineering and Physical Security:** These aspects are outside the scope of a code audit.
*   **Economic Exploits & Game Theory (unless directly tied to code logic bugs):** While the design's economic incentives are important, this audit focuses on technical vulnerabilities in the code.
